# Фінансові правила та формули

Усі правила реалізовані як **чисті функції** у `src/domain/calculations/` і
покриті unit-тестами. Уся арифметика — в цілих копійках (`Money = number`).

## 1. Грошовий тип

- `100 грн = 10 000 копійок`.
- Ніяких обчислень бюджету через JavaScript float.
- `toMoney`, `addMoney`, `subMoney`, `mulMoney` — округлення до копійки.
- Форматування через `Intl.NumberFormat('uk-UA')`.

## 2. Витрати категорії

```
categoryActual = Σ(expense) + Σ(correction) − Σ(refund)   // лише для цієї категорії
```

Повернення (`refund`) зменшує факт категорії. Переказ у категорію **не** є
витратою.

## 3. Залишок категорії

```
limit     = planned + rolloverIn + transfersIn − transfersOut
available = limit − actual
usedRatio = actual / limit
```

Статуси: `idle` (0 витрат) · `ok` (<60%) · `fast` (60–85%) · `near` (85–100%) ·
`reached` (=100%) · `over` (>100% або перевитрата).

Статус передається **кольором + іконкою + текстом + числом** (не лише колір).

## 4. Місячні підсумки — без подвійного обліку

```
actualIncome     = Σ(income)
totalExpense     = Σ(expense) + Σ(correction) − Σ(refund)

confirmedPlans   = Σ(planned активних категорій)

unallocated      = actualIncome − confirmedPlans − Σ(reserve_deposit) − Σ(savings_deposit)

actualCashBalance = actualIncome − totalExpense
                    − (Σ(savings_deposit) − Σ(savings_withdrawal))
                    − (Σ(reserve_deposit) − Σ(reserve_withdrawal))

availableToSpend = max(unallocated, 0) + Σ(залишок планів категорій)

deficit          = unallocated < 0 ? −unallocated : 0
```

### Інваріанти

- **Переказ між бюджетними категоріями** не є новою витратою і **не змінює**
  `actualCashBalance` (лише перерозподіляє ліміти).
- **Переказ у накопичення/резерв** змінює доступність грошей, але **не**
  враховується як споживча витрата.
- Резерв, накопичення, розподілені та вільні гроші рахуються **окремо** — на
  головному екрані показані різними рядками.
- `expectedIncome` (очікуваний) ≠ `actualIncome` (фактичний). Доступними
  вважаються лише фактично отримані гроші.

## 5. Дохід частинами

`actualIncome = Σ` усіх операцій `income` місяця. Зарплата може прийти кількома
частинами (аванс + друга частина + підробіток) — кожна це окрема операція.

## 6. Дефіцит

Якщо сума планів + резервів + накопичень > фактичного доходу, майстер бюджету
**не дає мовчки підтвердити** — вимагає явно вказати джерело покриття.

## 7. Рекомендації сум (`recommendations.ts`)

Без ШІ та зовнішніх API. Враховують медіану, середнє за 3 міс, факт минулого
місяця, кількість місяців даних, частоту перенесень, мінімум/бажане, пріоритет,
рідкісні викиди.

- **Стабільна регулярна категорія:** `0.6 × середнє(3 міс без викидів) + 0.4 ×
  факт минулого місяця`.
- **Нестабільна категорія:** медіана без викидів.
- **Критична (пріоритет 1):** не опускається нижче бажаної суми.
- **Рідкісний великий викид** (> 2.5× медіани): пропонується звичайний ліміт +
  окреме поповнення цільового резерву (викид розмазується на ~6 міс). Разовий
  великий ветеринарний рахунок **не** стає нормою наступних місяців.

Кожна рекомендація має числове пояснення, напр.:
«За останні 3 місяці середня витрата — 5 760 грн»,
«Минулого місяця використано лише 3 800 грн із 5 000 грн».

## 8. Переноси при нестачі — безпечний порядок

Джерела пропонуються у порядку:
нерозподілені → розваги → комфорт → змінні категорії → місячний резерв →
накопичення (після окремого попередження).

**Ніколи не пропонуються як джерело** (пріоритет 1): ліки, обов’язкове
лікування, критичні витрати на тварин, оренда, комуналка, мінімум продуктів.

Кожен перенос — окрема операція, що зберігає: суму, джерело, отримувача, дату,
причину, ініціатора, залишок джерела **до** і **після**.

## 9. Пріоритети

1. Критично обов’язкове · 2. Базові потреби · 3. Здоров’я і стабільність ·
4. Резерви і накопичення · 5. Комфорт · 6. Розваги.

Користувач може тимчасово підвищити категорію до критичної в конкретному місяці
(`criticalOverride`).

## 10a. Виправлення помилково введених операцій (v0.3)

`updateTransaction(id, patch)` редагує `expense`/`income`/`refund` **на тому
самому id**, без створення нового запису. Баланс змінюється рівно на різницю
між старим і новим значенням — подвійного обліку немає (перевірено тестами
TEST A–D у `src/tests/transactionEdit.test.ts`).

Перекази (`category_transfer`-подібні операції — `reserve_withdrawal`,
`savings_withdrawal` та сам `Transfer`) **не можна** редагувати напряму:
`updateTransaction` кидає помилку для будь-якого типу, крім
`expense`/`income`/`refund`. Щоб «виправити» переказ, використовується
`deleteTransfer(id)` — м'яке скасування (`Transfer.deletedAt` + повернення
балансу резерву/накопичення, якщо джерело було звідти) — і створення нового
коректного переказу через `doTransfer`. `computeCategoryState`/`loadMonthView`
фільтрують перекази з `deletedAt`, тому скасований переказ одразу перестає
впливати на ліміти категорій.

## 10b. Валідація переносів (v0.3)

`doTransfer` тепер відхиляє на рівні репозиторію (до будь-якого запису в БД):
- суму `<= 0`;
- перенос у ту саму категорію, що є джерелом;
- відсутню/неактивну категорію призначення;
- суму, що перевищує реальний доступний залишок джерела (категорія/резерв/
  накопичення) — UI-валідація сама по собі недостатня.

Запис резерву/накопичень, пов'язаної операції зняття та самого `Transfer`
виконується атомарно в одній Dexie-транзакції (`db.transaction('rw', …)`).

## 10c. Тижневий бюджет (v0.3) — не ділиться на 4

`computeWeeklyBudget` (`src/domain/calculations/weekly.ts`) — чиста проєкція,
не окрема таблиця. Тиждень = понеділок–неділя, обрізаний межами місяця.

```
remainingSpendable = max(totals.availableToSpend, 0)   // НЕ actualCashBalance
safeWeeklyBudget    = round(remainingSpendable × daysLeftInWeek / daysLeftInMonth)
```

`availableToSpend` навмисно обрано базою замість `actualCashBalance`, бо
останній включає гроші, вже призначені на резерви/накопичення — вони не
мають вважатися «вільними для витрат цього тижня».

## 10. Закриття та відсоток накопичень

```
savingsRateBps = round(toSavings / actualIncome × 10000)   // 100 bps = 1%
```

Закритий місяць редагувати не можна без окремого підтвердження повторного
відкриття (`reopenMonth`, з інкрементом `reopenCount` та аудитом).
