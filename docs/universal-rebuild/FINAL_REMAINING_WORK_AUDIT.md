## 3. Bug found and fixed this session

`scripts/verify-universal-domain.mjs` used a naive `/\bany\b/g` regex to enforce "the universal
domain must not use TypeScript's `any` type." It matched the **English word** "any" inside comments
and error-message strings (e.g. "...does not match any source entity"), not actual `any`-type usage.
This made `npm run verify:domain` **fail unconditionally** on 3 legitimate matches, and — because
nothing in the aggregate scripts (`lint:runtime`, `verify:universal-regression`, Stage-17 harness)
calls `verify:domain`, the false failure had been silently latent since Stage 7 (`017c1ac`), never
caught by any of the "PASS" reports. Fixed by stripping comments/string literals before matching
real code. Now: `{"ok":true,"anyCount":0}`. This is exactly the "formally closed but not proven"
class of defect this audit was asked to find — a verification script whose own bug had never been
exercised because it wasn't wired into any aggregate gate.

## 4. Genuine, currently-documented domain gaps (honest, already known in code — not hidden)

The domain's own ownership registry, `src/domain/complex-authority/aggregateOwnership.ts`, is
itself an accurate, non-aspirational source of truth (verified against real UI call sites). Current
real gaps, confirmed against code:

| Gap | Campaign | Root cause | Ownership registry status |
|---|---|---|---|
| Placement create | Greyholm + UC | id generated by `uid('pin')` / plain dispatch in store, no coordination with universal domain | `excluded-id-coordination` (UC) / `patch-merge-deferred` (Greyholm) |
| Placement move/remove | **Greyholm only** | overlay patch-merge; never routed through complex authority (UC side IS wired) | `patch-merge-deferred` |
| Party location move | Greyholm | `SET_CURRENT_LOCATION` is a coupled multi-slot legacy action (also clears `currentMapPosition` + `partyRouteProgress`) | `excluded-coupled` |
| Route progress advance/clear | Greyholm | `SET_PARTY_ROUTE_PROGRESS` also clears `currentMapPosition` (multi-slot) | `excluded-coupled` |
| Presented card | UC | no presented-card action exists in the user-campaign store at all (capability gap, not just wiring) | `no-ui-action` |
| Reveal | UC | `toggleReveal` is coupled (also flips `mapPlacements[].visibleToPlayers` + `images[].playerSafe`) | `excluded-coupled` |

All six rows are engine-capable and Node-proven (`scripts/stage16/runComplex.mjs`) but legacy-owned
in the real UI. Closing them safely requires either (a) deterministic ID coordination between the
store and the universal domain for *-create commands, or (b) decomposing multi-slot legacy actions
into ordered single-aggregate commands without changing user-visible behavior — both are real
design/engineering work on core gameplay mechanics (party movement, reveal), not one-line fixes.
**Decision this session:** given the correctness risk of touching live party-movement/reveal logic,
this work was not attempted under this pass; it is left as the top local backlog item (see §6)
rather than rushed. This is an honest scope decision, not a discovered blocker.
