# Банківська звірка — дизайн майбутнього релізу (не реалізовано)

Короткий backlog-документ. Ціль цього релізу (v0.3) — переконатися, що
поточна модель `Transaction` не потребує переробки, щоб додати звірку
пізніше. CSV/XLSX-парсер і UI цього релізу **не реалізовуються**.

## Чому поточна модель готова

`Transaction` (`src/domain/models.ts`) уже має все необхідне для майбутнього
matching без зміни схеми:

- `id`, `date`, `amount`, `categoryId`, `note`, `paymentMethod` — достатньо
  полів для порівняння з рядком банківської виписки.
- `deletedAt` (м'яке видалення) — дозволяє позначити операцію
  «підтверджену/відхилену» без фізичного видалення.
- `relatedTransactionId` — вже використовується для refund/correction,
  можна перевикористати для зв'язку «імпортована операція → підтверджена
  користувачем локальна операція».

## Майбутній потік (ескіз)

```
виписка банку
  ↓ normalize (дата, сума, опис → уніфікований формат)
  ↓ candidate matching (за сумою + датою ± N днів + fuzzy-опис)
  ↓ exact / probable / unmatched / conflict
  ↓ підтвердження користувача
  ↓ імпорт відсутніх операцій
```

## Критичне правило

Жодних тихих дублікатів. Якщо банківський рядок імовірно відповідає вже
існуючій операції — не створювати нову; або зв'язати (`relatedTransactionId`),
або дати користувачу явно вибрати «це дублікат / це нова операція».

## Що НЕ робити заздалегідь

Не додавати поля на майбутнє (наприклад `externalId`, `bankAccountId`) у
`Transaction` до того, як реально почнеться реалізація — вони будуть додані
разом з відповідним Dexie `version(n)` у тому релізі, коли парсер дійсно
пишеться.
